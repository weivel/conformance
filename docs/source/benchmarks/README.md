The benchmarks folder holds the core control call benchmark and every timing budget weivel holds, as data beside the one program that measures the core; what each budget means and how each number was measured is in [the benchmarks doc](../../benchmarks.md). `budget.txt` is the core's one line, read by the program's `gate`; `c.txt`, `java.txt` and `typescript.txt` are the bounds each language reads from the kit commit it pins, so a language's ratio bounds change only by a commit here and a pin move there. The program links the core alone, measures one `weivel_get_service` on a warm core with a monotonic clock, and keeps two exit codes apart: 1 is over budget, 2 is a budget it cannot read or a run that measured nothing, so a broken budget never reads as a slow core. Its tests run it against malformed and impossible budgets under `test/fixtures/benchmark/`, and the committed budget is gated in a Release build only, since a timing verdict from an unoptimised build means nothing. Every `<language>.txt` in this folder gets a `language_budget_of_<language>_is_well_formed` test without a line of CMake, so a new language's file is checked the moment it lands.
